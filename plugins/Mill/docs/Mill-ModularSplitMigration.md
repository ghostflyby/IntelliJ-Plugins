# Mill Modular Split Migration (Plugin Model v2)

Status: Implemented
Completed: 2026-11-24
Reference example: `plugins/WorkspaceMcpTools/docs/WorkspaceMcpTools-ModularSplitMigration.md`

## What Changed

The plugin is now a modular (Plugin Model v2) plugin with two content modules and a split-mode
development loop:

| Module                          | Gradle project | Loading                            | Content                                                                                        |
|---------------------------------|----------------|------------------------------------|------------------------------------------------------------------------------------------------|
| `dev.ghostflyby.mill.shared`    | `shared`       | `required`                         | `MillConstants`, `Bundle` + messages, `MillImportDebugLogger`, settings state (`MillSettings`, `MillLocalSettings`, `MillProjectSettings`, `MillSettingsListener`, `MillExecutableSource`/`MillExecutableConfiguration`), `MillDiscoveredModule`, `MillProjectResolverSupport` |
| `dev.ghostflyby.mill.backend`   | `backend`      | `embedded`, `required-if-available="intellij.platform.backend"` | Everything else: external-system manager/resolver/task manager, `command/`/`project/`/`sdk/`/`script/`, data services, open/link flow, settings UI, tool window, actions, notification group |

- Root `plugin.xml` declares only metadata plus `<content>` and the Marketplace error handler;
  all extensions/actions/dependencies moved into the backend module descriptor
  (`backend/src/main/resources/dev.ghostflyby.mill.backend.xml`), which gates itself on
  `intellij.platform.backend` (+ `com.intellij.modules.externalSystem`, the Java and Scala
  plugins, and the shared module).
- Root build: `pluginModule(shared)` + `pluginComposedModule(backend)` + `splitMode = true` +
  `pluginInstallationTarget = BACKEND`. `runIdeBackend` / `runIdeSplitMode` (generated by IJPG)
  give the local two-process debugging loop.
- `modules/intellij-shared` stays embedded into the main jar via `pluginComposedModule` at the
  root, exactly as before: the settings UI lives on the backend (main classloader), which sees
  `lib/*.jar`, so no third content-module classloader is needed for `EditableHintedComboBox`.

## Why No Frontend Content Module

Everything Mill ships is backend-native: project import and task execution run in the
external-system remote process and backend data services, and the tool window / settings /
actions read `MillSettings` state that only exists on the backend; backend Swing replicates to
the JetBrains Client, so remote development still gets the full UI. A separate frontend module
would either duplicate settings state per process or need a Remote Topic bridge that does not
exist yet. This mirrors the deliberate "backend-only" phase recorded in
`WorkspaceMcpTools-BackendOnlyRuntime.md`; the shared module keeps the seam open for a future
frontend module (e.g. once notifications move to a Remote Topic bridge — the same limitation
WorkspaceMcpTools documents for split-mode balloons applies to Mill's import notifications).

## Platform Facts Carried Over

- Content-module classloaders never see the plugin's `lib/*.jar`, which is why the backend is
  embedded (it needs kotlinx-serialization for the `show` JSON import) — same rationale as
  WorkspaceMcpTools' backend.
- `MillExecutionSettings` and the `Mill*Data` payloads stay in the backend (main jar) because
  they cross into the external-system remote process, whose classpath is derived from the main
  plugin classloader.
- Cross-module APIs in `shared` became explicitly `public` (`Bundle`, `MillImportDebugLogger`,
  settings classes, `MillDiscoveredModule`, parts of `MillProjectResolverSupport`); ABI dumps
  live at `shared/api/shared.api` and `backend/api/backend.api` (the root dump stays empty,
  matching WorkspaceMcpTools).
- IJPG names module jars and sandboxes per-project; the repo conventions now handle both
  centrally (see `docs/Sandbox-Naming.md` at the repository root).

## Verification Status

- `:plugins:Mill:shared:test`, `:plugins:Mill:backend:test`, `:plugins:Mill:test` green
  (root pins the descriptors via `PluginDescriptorTest` / `BackendDescriptorTest`).
- Remote-process import regression: the resolver/task-manager classes and serialized settings
  remain in the main jar, so the remote classpath derivation is unchanged; the settings state
  file format is unchanged (`MillSettings`/`@State` names preserved through the Java→Kotlin
  conversion).
- Interactive `runIdeSplitMode` pass (open a Mill project, check import + tool window + settings
  in the JetBrains Client) still needs one manual run — the same pending pass
  WorkspaceMcpTools tracked at its 2.1.0 migration.
