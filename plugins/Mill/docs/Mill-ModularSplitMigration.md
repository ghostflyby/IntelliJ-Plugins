# Mill Modular Split Migration (Plugin Model v2)

Status: Implemented
Completed: 2026-11-25
Reference example: `plugins/WorkspaceMcpTools/docs/WorkspaceMcpTools-ModularSplitMigration.md`

## What Changed

The plugin is now a modular (Plugin Model v2) plugin with three content modules and a
split-mode development loop:

| Module                          | Gradle project | Loading                            | Content                                                                                        |
|---------------------------------|----------------|------------------------------------|------------------------------------------------------------------------------------------------|
| `dev.ghostflyby.mill.shared`    | `shared`       | `required`                         | `MillConstants`, `Bundle` + messages, `MillImportDebugLogger`, settings state (`MillSettings`, `MillLocalSettings`, `MillProjectSettings`, `MillSettingsListener`, `MillExecutableSource`/`MillExecutableConfiguration`), pure probe result data (`MillExecutableDiscovery`/`MillExecutableProbeResult`), `MillTasksData`, `MillDiscoveredModule`, `MillProjectResolverSupport`, the RPC API + DTOs |
| `dev.ghostflyby.mill.frontend`  | `frontend`     | default (frontend)                 | Settings UI (`MillConfigurable`, view, view model, selector), tool window factory/task tree/view contributor, link/reload/run-task actions, run-configuration type, open/link flow (`MillProjectOpenProcessor`, `MillOpenProjectProvider`, `MillUnlinkedProjectAware`), import refresh callback, notification group |
| `dev.ghostflyby.mill.backend`   | `backend`      | `optional`, `required-if-available="intellij.platform.backend"` | External-system manager/resolver/task manager, command layer (`MillCommandLineUtil`) and execution target/settings, language-agnostic project import (`project/`), Java/JDK import (`java/`), Scala SDK import (`scala/`), build-script integration (`script/`), data services, file type/roots/resolve-scope integration |
| `dev.ghostflyby.intellij.shared`| `modules/intellij-shared` | `required`                | Shared widgets (`EditableHintedComboBox`) used by the settings UI; Mill ships them as a content module because content-module classloaders cannot see `lib/*.jar` |

- Root `plugin.xml` declares only metadata plus `<content>` and the Marketplace error handler;
  each module descriptor declares its own dependencies and extensions.
- Root build: `pluginModule(shared)` + `pluginModule(frontend)` + `pluginModule(intellij-shared)`
  + `pluginModule(backend)` + `splitMode = true` +
  `pluginInstallationTarget = BOTH`. `runIdeBackend` / `runIdeFrontend` / `runIdeSplitMode`
  (generated by IJPG) give the local two-process debugging loop.
- The backend is a **real content module**, not `embedded`: the platform ignores
  `required-if-available` for `embedded`/`required` modules
  (`PluginContentDescriptor.ModuleItem.determineLoadingRule`), so an embedded backend still loaded
  in a split-mode frontend and failed with "requires plugin `intellij.platform.backend` to be
  installed" (and ran the resolver there). With `loading="optional"` the module is skipped when
  the target module is unavailable and becomes `required` when it is present.
- The external-system integration is split by platform extension-point ownership: UI-bearing
  points (`projectConfigurable`, `toolWindow`, `externalSystemViewContributor`, `actions`,
  `notificationGroup`, `projectOpenProcessor`, `configurationType`,
  `externalSystemUnlinkedProjectAware`) live in the frontend module; resolver-side points
  (`externalSystemManager`, `externalProjectDataService`, `additionalLibraryRootsProvider`,
  `resolveScopeEnlarger`, `fileTypeOverrider`, `scalaLanguageDerivative`) live in the backend.

## Why the UI Lives in the Frontend

The previous backend-only phase put settings/tool window on the backend and relied on
`pluginInstallationTarget = BACKEND`; that kept the plugin out of the JetBrains Client entirely,
so its UI could not appear in remote development. The frontend module restores the intended
split-mode behavior: the platform loads the plugin on both sides, routes frontend extension
points to the client and backend extension points to the backend, and the external-system
machinery synchronizes the data the view contributor and settings UI consume.

## Frontend Executable Probing over RPC

Executable discovery and version probing spawn processes on the host and read host paths, so they
run in the IDE backend. The frontend reaches them through the platform's split-mode RPC:
`MillBackendRpcApi` (`shared`) declares `suspend` calls with serializable DTOs and resolves the
implementation through `RemoteApiProviderService`; the backend registers
`MillBackendRpcApiProvider` under `com.intellij.platform.rpc.backend.remoteApiProvider` and
implements the calls with `MillCommandLineUtil` + `MillExecutionTargets`. In a monolith the same
descriptor resolves to the local implementation, so behavior there is unchanged; in a split-mode
frontend the calls cross to the backend. If the backend is unavailable, the view model degrades
to no discovery and no version hints instead of spawning anything on the client.

The `rpc` Gradle plugin (published from the JetBrains `intellij-dependencies` repository) drives
the descriptor/client-stub code generation and must match the repository's Kotlin compiler line;
`shared`, `frontend` and `backend` apply it together with `org.jetbrains.kotlin.plugin.serialization`.

## Platform Facts Carried Over

- Content-module classloaders never see the plugin's `lib/*.jar`; the backend module therefore
  relies only on platform-provided modules, declared in its descriptor (`intellij.platform.backend`,
  `intellij.platform.externalSystem{.impl}`, the RPC/kernel modules and the platform's
  `intellij.libraries.kotlinx.serialization.*`). Nothing plugin-local sits outside the module jar.
- `MillExecutionSettings` lives in the backend module jar and crosses into the external-system
  remote process; the frontend only sees the RPC DTOs. `MillExecutableDiscovery` and
  `MillExecutableProbeResult` stay in `shared` because both the backend implementation and the
  frontend view model consume them, but they are pure data — no process handling is shared.
- `MillTasksData` lives in `shared` because both the backend resolver (produces the DataNode)
  and the frontend view contributor (renders it) reference the key.
- Cross-module APIs in `shared` are explicitly `public` (`Bundle`, `MillImportDebugLogger`,
  settings classes, the pure probe result data, `MillTasksData`, `MillDiscoveredModule`,
  `MillProjectResolverSupport`, the RPC API/DTOs);
  ABI dumps live at `shared/api/shared.api`, `frontend/api/frontend.api` and
  `backend/api/backend.api`.
- IJPG names module jars and sandboxes per-project; the repo conventions now handle both
  centrally (see `docs/Sandbox-Naming.md` at the repository root).

## Verification Status

- `:plugins:Mill:shared:test`, `:plugins:Mill:frontend:test`, `:plugins:Mill:backend:test`,
  `:plugins:Mill:test` green (root pins the descriptors via `PluginDescriptorTest`,
  `BackendDescriptorTest` and `FrontendDescriptorTest`).
- `buildPlugin` lays the modules out as `lib/modules/dev.ghostflyby.mill.shared.jar`,
  `lib/modules/dev.ghostflyby.mill.frontend.jar` and
  `lib/modules/dev.ghostflyby.intellij.shared.jar`, with the backend composed into the main jar.
- Remote-process import regression: the resolver/task-manager classes stay in the main jar and
  the serialized settings remain on the remote classpath; the settings file format is unchanged
  (`MillSettings`/`@State` names preserved through the Java→Kotlin conversion).
- Interactive `runIdeSplitMode` pass (open a Mill project, check import + tool window + settings
  in the JetBrains Client) still needs one manual run — the same pending pass
  WorkspaceMcpTools tracked at its 2.1.0 migration.
